Three ingestion methods were run on the same 7 pages and scored against a **reference copy**: the visible
main-column text captured in a real Chrome session (method C), verified byte-for-byte with an in-browser
SHA-256. Generated by `scripts/compare_scrapers.py`.

| Method | How |
|---|---|
| **A. requests + BeautifulSoup** | HTTP GET of server HTML (robots.txt, UA, 1 req/s) → html5lib DOM → page parsers |
| **B. Selenium + BeautifulSoup** | Headless Chrome renders JS → `page_source` → same page parsers |
| **C. Claude-in-Chrome** | Agent opens each page in a real browser and copies the visible text |

## What happened, method by method

### A. requests + BeautifulSoup: **chosen**
- **100% of the visible content** on all 7 pages, **0 leaked prices**, 0% translated text.
- It also gets **real page content a visitor can't see**, which the bot needs:
  - **43 FAQ answers.** The compare page's 12 answers sit in collapsed `<details>`, so they're invisible to a browser text copy.
  - **124 video descriptions.** These exist only in JSON-LD `VideoObject`.
  - **Listing notes** ("1 session" vs "5 sessions"). These are in the page's inline `center_data`, and comparisons are wrong without them.
  - **A missing table name filled from JSON-LD:** price-list row 4 → "Cancer Treatment".
- **Deterministic:** two fetches gave the same content hash on 7/7 pages, so refresh re-embeds only pages that changed.
- **Fastest:** 8.4s total (≈1 req/s by design). Pure Python, so it runs on Streamlit Cloud with no browser binary.
- **Two fixes were needed:**
  - **Parser choice.** The pages have unbalanced tags. `lxml` nested the sidebar (quote form, site stats) inside `<main>`, and `html.parser` doesn't auto-close `<p>` before headings, which lost 19 sections per package. `html5lib` uses the same HTML5 algorithm as browsers and matches Chrome's DOM.
  - **Review cards.** The name is rendered after the text, so heading-based grouping gave each review to the previous reviewer. Each card is now one attributed line.

### B. Selenium + BeautifulSoup: **rejected (deleted after this test)**
- The site runs Google Translate (`gtranslate`) and chooses the language **by visitor IP**. From this machine, 5/7 pages came back **29–88% machine-translated into Urdu**, partly translated depending on timing (the adenocarcinoma page escaped only because translation hadn't finished).
- Forcing `--lang=en-US` / `accept_languages` made **no difference**: same result, which confirms the trigger is geo-IP, not browser locale. Any server-side browser deployed abroad would face the same lottery.
- Translation **damaged prices**: the cost-range table lost its "High" column ("$200 – $800" became "$200"), the anal package lost 6 FAQs, and price-row names turned into Urdu. That's exactly the "wrong price" failure the rubric punishes.
- Even on untranslated pages it adds **nothing**: the output was identical to requests (the compare page's "Load More" just re-renders the same 5 rows from inline JSON). It was also 2.9× slower, and Streamlit Cloud would need a Chrome binary.

### C. Claude-in-Chrome capture: **used only as the reference copy**
- It shows exactly what a visitor sees (verified with an in-browser SHA-256; the only differences were invisible `U+00A0` non-breaking spaces).
- It **misses hidden-but-real content**: collapsed FAQ answers, JSON-LD video descriptions, listing notes. It also has **no structure** (no headings or table cells as data), so structure-aware chunking and atomic price records are impossible.
- **It isn't automatable.** An agent has to drive a browser and relay the text, so it can't power Must-have #7 (refresh). And every character passes through an LLM, which is a risk in itself for a bot whose top rule is "never alter a price".
- It also showed that page JavaScript hides one price sentence ("prices range between ~~$18995 - $18995~~ in Tijuana"). Server HTML keeps it.

## Decision
**requests + BeautifulSoup (html5lib)** is the ingestion method. Selenium code and the dependency are removed. These results and `data/raw/chrome/` stay as evidence.
